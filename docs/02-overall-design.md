# 02 · 总体设计与架构

## 1. 问题定义

传统项目管理工具（Jira/Plane/Taiga）记录"人做了什么"，AI 编程工具（Copilot/Claude Code）加速"单人写代码"，两者之间存在断层：**没有一种系统把"安排 Agent 工作"本身作为一等公民的项目管理活动**。AgentPM 要补的正是这个断层：

- 项目经理安排的不是人，而是**角色化 Agent + 人工检查点**组成的工作流；
- 管理对象从"工单"升级为"工单 + 工件 + Agent 运行轨迹"；
- 信任问题（Agent 会不会乱来）由**权限分级 + 审批 + 不可变审计**解决，而不是"不许它动"。

## 2. 核心理念（四条，全部来自调研验证）

### 2.1 流程即图（Graph Engineering）

把 graph engineering 理念落到项目管理域：**项目是一张 DAG（Project Graph）**：

- **节点**有三类：`Phase`（阶段，如"需求分析"）、`Task`（任务，即工作项，挂 Agent 角色或人）、`Gate`（阶段门，人工审批点）；
- **边**有两类：`depends_on`（依赖，上游完成后下游才可启动）、`produces/consumes`（工件传递，如 PRD → 设计 → WBS）。

人的角色从"执行者"转变为**图的编排者（orchestrator）与守门人（gatekeeper）**：拖拽调整依赖、指派节点给 Agent 或人、在 Gate 上决定放行/打回。Agent 是图上的**执行器**：领到 Task 节点后以 Run 形式执行，轨迹挂在该节点上。

```
[需求 intake] ──▶ (Phase 需求分析) ──▶ ◆Gate: PRD评审 ──▶ (Phase 设计) ──▶ ...
                        │ 产出: PRD.md                        │ 产出: design.md
                        ▼                                     ▼
                  PM-Agent Run                          Architect-Agent Run
```

好处（相对黑盒"全自动"方案）：可解释（为什么这个任务现在跑）、可控（Gate 与权限）、可局部重跑（失败节点单独 retry，借鉴 LangGraph 子图重放）。

### 2.2 事件溯源（Event Sourcing）

借鉴 OpenHands 的"状态不存、日志推导"与 AG2 的 WAL：

- 一切写操作（人的与 Agent 的）都是事件，追加写入 `events` 表，**不可变**；
- 工作项状态、看板列、轨迹树、审计视图，全部是事件流的**投影（read model）**；
- 一次存储，三个用途：**当前状态**（投影）、**轨迹可视化**（Agent 事件流）、**审计**（审批与危险操作事件）。这是本方案避免"为轨迹和审计单独建三套系统"的关键决策。

### 2.3 工件即文件（Artifacts as Files）

借鉴 MetaGPT：PRD、系统设计、WBS、测试报告、发布说明均为 Markdown，存放在**项目内容仓（Git）**：

- 人类可 diff/评审/批注，Agent 可读取消费，格式对双方同等友好；
- Git 提交即天然版本史，"打回到上一版 PRD"= checkout；
- 代码类工件直接进代码仓的分支/PR，复用现有代码评审流。

### 2.4 人在回路是一等原语（HITL as Primitive）

借鉴 LangGraph：Agent 运行到**阶段门**或**危险工具调用**时 `interrupt()` 挂起并持久化 checkpoint；人在 WebUI 看到 pending 审批（含 diff），可 批准 / 拒绝 / **修改后恢复**（改 Agent 状态再 resume，比纯批准更强）。审批动作本身写审计事件。审批策略 fail-closed、单次授权（dsh 模式，见 05）。

### 2.5 会话为中心的交互（Conversation-Centric，v0.2 新增）

借鉴 dsh/pi 两个真实可用产品：**一切人机交互发生在持久对话中**。

- 层级为 项目 → 功能 → 对话（03 §1）：对话是交互的原子单元，挂载消息树（id/parentId，pi 模式）、Run、审批与提示词分层（L1 宪章/L2 简报/L3 指令）；
- 对话 = append-only 事件流，**随时可打断、可分叉、可恢复**（dsh：fork 血统 + 合成中断事件；pi：单文件内树状分支）；
- 执行前讨论、执行中纠正、执行后复盘都在同一持久上下文——避免上下文散落在轨迹注释里。

### 2.6 本体驱动的类型系统（v0.2 新增）

系统内核不硬编码"软件研发"世界观：工作项概念类型、状态机、阶段图模板、工件种类、可绑角色、NL 实体词典，全部由**项目本体**（`ontology.yaml`，Git 版本化）在建项目时编译驱动。简化自 semantica（Competency Questions、受控关系枚举、本体即数据），详见 08。

### 2.7 资产沉淀闭环（v0.3 新增）

项目是临时的，资产是复利的：**值得复用的工件经入库评审沉淀为组织级资产**（产品库/测试库/文档库），带来源链与引用链；任何项目的 Agent 可通过工具检索复用，改进后可再沉淀为新版本，形成"沉淀→复用→改进→再沉淀"的飞轮。资产的类型、库与生命周期同样由本体注册（08 §3），资产域详细设计见 09。

## 3. 使用体验的两个正交维度

### 3.1 导航层级：项目 → 功能 → 对话（v0.2）

用户的主动导航沿三层容器下钻，**每层有明确的"首屏问题"**：

| 层 | 容器 | 首屏问题 | 主要界面 |
| --- | --- | --- | --- |
| N1 | **项目 Project** | 项目健康吗？边界与进度如何？ | Dashboard、项目 Graph、审计 |
| N2 | **功能 Feature** | 这块需求推进到哪了？ | 功能页（看板切片/对话列表/工件切片） |
| N3 | **对话 Conversation** | 这次人机协作进行到哪一步？ | 对话视图（消息树+Agent 步骤+打断/恢复） |

- 工作项与 Run 挂在功能/对话之下（Item ∈ Feature；Run ∈ Conversation）；
- 编排图（Phase Graph）是项目层横切视图；轨迹是执行层的只读下钻；
- 详见 03 §1 与 06 §2/§3。

### 3.2 信息深度：新手 ↔ 专家（三态披露）

与导航层级正交：同一页面按使用深度渐进披露——新手只看主操作（批准按钮、发送框），专家通过右键菜单/快捷键/命令面板/上下文分层展开全部能力（06 §4）。**只用 N1 也能走完核心闭环；提示词四层（L1-L4）同样按此原则披露（03 §2）。**

### 模块职责要点

- **对话服务**：消息树（id/parentId）持久化、打断/继续/分叉、提示词分层（L1-L4）组装与版本管理、上下文预算与压缩缝（dsh 三事件锁）；
- **NL 命令路由（UI-Agent）**：把自然语言解析为应用 API 调用序列；只读直执、写操作预览确认；实体词典来自本体（详见 06 §5）；
- **本体服务**：加载/校验 `ontology.yaml`，编译为类型注册表（工作项类型/看板列/阶段图/角色挂点/资产类型与库/NL 词典），`ontology.changed` 驱动重载（详见 08）；
- **资产服务**（v0.3）：沉淀流程（含入库 Gate）、资产仓 Git 读写、FTS/向量检索、引用登记与来源/引用链维护、supersede 版本管理（详见 09）；
- **Orchestrator**：唯一有权启动/暂停 Run 的组件。监听事件，判断"某工作项的依赖全部 done → 就绪"，按指派分发；Gate 节点到达时生成 pending 审批而非启动 Run；
- **Agent Runtime**：以 LangGraph 为执行引擎。角色 Agent = 一个子图（system prompt + 工具集 + 产出 schema，YAML 加载）；Run = 子图执行，thread_id = run_id，天然获得 checkpoint 与恢复。压缩、审批、持久化均为**能力缝**（capability seam，dsh 模式）：MVP 用默认实现，接口可替换；
- **事件总线**：同步落库 + 异步投影 + SSE 广播；**live 与 replay 共用同一投影函数**，实时视图即历史回放；
- **投影器**：纯函数 `fold(events) → read model`，新增视图不加存储（扩展性关键）。

## 5. 技术选型

| 层 | 选型 | 理由（含替代项） |
| --- | --- | --- |
| 后端 | Python 3.12 + FastAPI | Agent 生态主语言；异步 + 自动 OpenAPI（API-first） |
| Agent 运行时 | LangGraph + 其 SqliteSaver/PostgresSaver | interrupt/checkpoint/time-travel 免自研（替代：自研状态机，成本高） |
| LLM 接入 | Provider Adapter（OpenAI 兼容协议优先） | 一套接口换模型；UI-Agent 可单独配小模型（意图解析便宜快速） |
| 元数据存储 | SQLite（MVP）→ PostgreSQL（V2） | 单文件零运维起步，schema 兼容迁移 |
| 内容存储 | 每项目一个裸 Git 仓（git 命令或 dulwich） | 工件/提示词/本体的版本史免费获得 |
| 前端 | React + Vite + TypeScript + Tailwind + **shadcn/ui（Radix 原语）+ lucide-react** + React Flow + cmdk + Sonner + TanStack Query/Table | 组件质感与图标语言直接复用开源（视觉对标 Linear/Plane/Huly，复用清单见 07 §2.5）；React Flow 成熟的 DAG 可视化/编辑；SSE 用原生 EventSource |
| 实时 | SSE（Server-Sent Events） | 单向事件流足够，避免 WebSocket 复杂度（V2 需双向再换） |
| 部署 | docker-compose 单机一键起 | MVP 目标：`docker compose up` 即可用 |

**极简纪律**（pi 标尺）：每个候选特性先问"能否用一个文件/一个简单机制替代"——提示词是文件、本体是文件、规则 V2 前只有三个开关；内核（agent loop + 事件日志 + 投影）保持小，其余走能力缝与插件位（dsh 模式）。

## 6. 关键非功能决策

- **安全边界**：Agent 的文件写入限制在项目内容仓内；命令执行默认禁止（V2 引入 Docker 沙箱后开放，借鉴 OpenHands）；外发类工具（发邮件/开 PR）标记 dangerous 恒需审批；
- **可恢复性**：服务重启后从 checkpoint 表恢复挂起中的 Run；事件表是最终事实源；
- **多项目并发**：MVP 单用户多项目；多租户/权限体系放 V3；
- **成本可见**：每个 span 记录 token 用量，Dashboard 聚合展示（借鉴 Langfuse 上卷）。
