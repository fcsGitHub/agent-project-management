# 03 · 使用流程与层级模型（详细用户旅程）

> v0.2：按评审意见重写。以**用户典型使用流程**为主线组织本册：先定义"项目 → 功能 → 对话"的层级模型与提示词分层披露、随时可打断的持久化语义，再给出 9 条端到端详细剧本（v0.3 增流程 9 资产沉淀与复用），最后用"流程 → 功能"核对表验证功能完备性。生命周期六阶段建模收缩为 §6。

## 1. 信息架构：项目下挂功能，功能下挂对话

```
Workspace
 ├─ 资产库（Asset Libraries，组织级累计资产：产品库/测试库/文档库，见 09）
 └─ Project（项目）──────────── 本体(ontology)决定项目"长什么样"：概念类型、阶段图、角色
     ├─ 工件集（内容仓 Git：PRD/设计/报告…）
     ├─ Phase Graph（阶段图：编排视图，横切所有功能）
     └─ Feature（功能）──────── 一个需求/模块/Epic 的推进单元
         ├─ 工作项（Item：task/bug/test…，挂在功能下）
         ├─ 工件切片（功能相关的 PRD 章节、设计、验收标准）
         └─ Conversation（对话）── 人机交互的原子单元：持久、可打断、可分支
             ├─ 消息树（id/parentId，pi 模式：单流内天然分支）
             ├─ Run（Agent 自主执行段，绑定图节点/工作项）
             ├─ 审批点（interrupt 挂起）
             └─ 提示词层（本层指令 + 继承上层上下文）
```

三类容器的职责边界：

| 容器 | 回答的问题 | 生命周期 | 典型内容 |
| --- | --- | --- | --- |
| **Project** | 这个项目是什么、为什么、边界在哪 | 长（周/月） | 本体实例、里程碑、成员、审批策略、项目宪章 |
| **Feature** | 这块需求推进到哪了 | 中（天/周） | 工作项切片、小图（功能内依赖）、工件切片、进度 |
| **Conversation** | 人和 Agent 这次具体怎么协作的 | 短（分钟/小时），可长期挂起 | 消息树、Run 轨迹、审批、上下文层 |

**对话是万能挂载点**——系统中一切人机交互都发生在某个对话里：

| 对话类型 | 绑定 | 例子 |
| --- | --- | --- |
| 起草型 | Feature | 与 PM-Agent 讨论并生成 PRD |
| 执行型 | Item + 图节点 | Dev-Agent 执行任务 T7 的 Run 所在对话 |
| 评审型 | Approval | PRD 评审/代码评审的问答与批注 |
| 临时型 | Feature 或无 | "帮我看看这个报错"；用完可归档或升级为执行型 |
| 操作型 | 全局 | 自然语言操作页面的短对话（见 §4 流程 5 与 06 文档） |

> 与 v0.1 的关系：原"Run 直接挂在 Item 上"细化为"Run 在对话内、对话绑定 Item"。好处：执行前的讨论、执行中的纠正、执行后的复盘都在同一持久上下文里，而不是散在轨迹注释中。

## 2. 提示词分层披露（按层级）

每个对话的**有效提示词**由四层叠加而成，**上层对下层继承、下层可覆盖**。每层默认折叠、按需披露，且**可见、可编辑、可版本化**——这是"按层级披露提示词"的具体设计：

| 层 | 名称 | 内容 | 默认可见性 | 谁可编辑 | 变更生效 |
| --- | --- | --- | --- | --- | --- |
| L0 | 全局系统提示 | 产品内置：安全规范、输出格式、工具使用规范 | 高级模式可查看 | 仅部署配置 | 即时（全局） |
| L1 | **项目宪章** charter | 项目目标/背景/边界、技术约束、本体概念表（本项目有哪些领域概念与关系）、角色配置摘要 | 项目设置页；对话内"上下文"抽屉第 1 层 | 项目管理员 | 保存后对新消息生效，历史消息不重写 |
| L2 | **功能简报** brief | 该功能的 PRD 摘录、验收标准、相关设计链接 | 功能页"简报"卡；对话抽屉第 2 层 | 功能负责人 | 同上 |
| L3 | **会话指令** instruction | 本对话的任务指令（"请为 T7 生成导入解析模块并自测"） | 对话顶部常驻摘要行，点击展开全文 | 任何人（自己发起的对话） | 编辑后可选择"重发生效"（作为新消息注入） |
| L4 | 角色提示词 | Agent 角色 YAML 中的 system prompt | 高级模式（角色管理页） | 项目管理员 | 新 Run 生效 |

交互规则：

1. **披露而非堆叠**：对话界面默认只显示 L3 摘要一行 + 「-context 上下文」chip；点击展开分层查看（L1→L4 逐层折叠），每层带"谁在何时改过"的版本史；
2. **有效提示词预览**：「上下文」抽屉底部有"查看合并后的有效提示词"（含每段来源标注），供高级用户与调试使用（借鉴 dsh "模型可见即入日志"原则——模型看到的一切都能被检查）；
3. **编辑即版本**：改任何层生成 `prompt.updated` 事件 + Git 提交（提示词模板存内容仓 `prompts/` 目录），回滚 = 恢复旧版本；
4. **新增对话的默认行为**：从功能页发起 → 自动继承 L1+L2，用户只需写 L3；从模板发起（如"PRD 起草"）→ L3 预填模板；
5. **上下文预算**：各层有 token 预算（L1≤500、L2≤800），超限提示裁剪；长对话压缩（compact）时 L1/L2 永不丢弃，只压缩对话内历史（dsh 三事件锁模式）。

## 3. 持久化与随时打断

### 3.1 持久化语义

- 对话 = append-only 消息事件流（`message.created` …），**唯一真源**；看板/轨迹/审计都是它的投影；
- 消息树：每条消息 `id/parentId`（pi 模式），打断后改道 = 从某消息分叉新枝，原枝保留；
- Agent Run 的 checkpoint 在每次工具调用前后落盘（LangGraph checkpointer）；服务重启后 `running` 对话自动恢复到最近 checkpoint，`interrupted` 对话继续等审批；
- 崩溃安全：中断处写入合成 `run.interrupted` 事件配平（dsh 模式），日志永不截断。

### 3.2 可打断点全景

| 时刻 | 怎么打断 | 打断后 | 恢复方式 |
| --- | --- | --- | --- |
| Agent 执行中 | 对话内「⏸ 打断」按钮 / 直接输入消息（自动转为打断+指令） | Run 挂起，已完成步骤保留，产生 interrupt 事件 | 「继续」按钮（从 checkpoint）/ 带新指令继续（注入后 resume） |
| 等待审批中 | 无需打断（本来就挂起） | — | 审批中心批准/拒绝/改后恢复 |
| 空闲对话 | 归档或挂起 | 状态=挂起，不出现在活跃列表 | 重新打开即续（上下文完整） |
| 任何历史时点 | 轨迹/消息树上「从此分叉」 | 新建分支对话，血统记 parent+seed（dsh 模式） | 分支即新对话，原对话只读保留 |
| 批量执行中 | 取消队列中未启动的 Run | 已启动的走到下一个可打断点 | 重新批量启动 |

### 3.3 体验承诺（写进验收标准）

1. 刷新/关页/重启服务，任何对话回来时**状态与上下文无损**；
2. 打断延迟 < 1s（打断是本地状态切换，不等模型返回）；
3. 每条 Agent 消息都能展开看到：触发的工具、读写的工件、耗时与 token；
4. 用户对提示词的任何修改都有版本可回滚，且能看出"改前 vs 改后"的 Agent 行为差异（对照两个分支对话）。

## 4. 典型用户流程（详细剧本）

> 每条剧本按"步/用户看到并做什么/系统做什么/落盘什么"展开，用于**验证功能完备性**（见 §5 核对表）。

### 流程 0：首次上手（目标：5 分钟内见到第一个 Agent 产出）

| 步 | 用户操作 | 系统行为 | 落盘 |
| --- | --- | --- | --- |
| 1 | 打开首页，点「新建项目」 | 出现三字段极简表单：项目名 / 一句话需求 / 模板（默认"轻量"） | — |
| 2 | 填写并提交 | 建项目 + 默认本体实例化 + 建首个 Feature「MVP」+ 内容仓初始化 | project.created 等事件 |
| 3 | 看到"项目就绪"引导页，只有一个高亮按钮「和 PM-Agent 谈需求」 | 创建起草型对话，L3 预填"基于以下需求起草 PRD：…" | conversation.created |
| 4 | （可选）点「上下文」chip | 抽屉披露 L1 宪章（自动生成初稿）/ L3 指令 | — |
| 5 | 点「发送」 | PM-Agent 起草 PRD；过程流式可见（思考/写文件步骤折叠显示） | message.*、run.*、artifact.committed |
| 6 | Agent 完成，卡片提示「请求 PRD 评审」 | 生成审批；通知徽标 +1 | approval.requested |
| 7 | 点开审批：预览 PRD → 「批准」 | Planner-Agent 对话自动接续（计划确认流程开始） | approval.granted |

### 流程 1：创建第二个功能（体现"项目下挂功能"）

1. 项目页左侧功能列表点「＋ 新功能」，输入功能名与一句话描述；
2. 系统建 Feature + 功能简报（L2）初稿（由 PM-Agent 30 秒生成，可改）；
3. 用户选择功能模板：空白 / 从 PRD 章节 / 复制现有功能结构；
4. 功能页 = 该功能的看板切片 + 小图 + 工件切片 + 对话列表四个 Tab；
5. 后续所有对话与工作项默认挂在此功能下；项目级 Graph 视图可看多功能的阶段并行。

### 流程 2：日常推进循环（对话内的"派工-观察-纠正"）

1. 功能页打开执行型对话（或从看板卡片「让 Agent 做」自动创建）；
2. L3 指令已含任务卡上下文；用户补充一句"注意用 pandas 不要用 openpyxl"；
3. Dev-Agent 执行：每个工具调用在对话内是一行可展开步骤（写文件、跑自测）；用户随时可以：
   - 点某步骤「查看 diff」→ 右抽屉看工件变更；
   - 直接输入"第 3 步的异常处理不对，改成重试三次"→ 自动打断并注入；
4. Agent 完成 → 卡片转 awaiting_review，对话挂起；
5. 用户在对话内点「验收」或去审批中心；批注写回对话，成为后续 Run 的上下文。

### 流程 3：打断-修改-恢复（评审重点场景）

| 步 | 用户操作 | 系统行为 | 落盘 |
| --- | --- | --- | --- |
| 1 | Agent 正在批量修改 5 个文件，用户发现方向错了，点「⏸ 打断」 | Run 在当前工具调用后挂起（已完成的 2 个文件保留） | run.interrupted |
| 2 | 用户在对话里输入纠正指令，并点「上下文」→ 编辑 L2 功能简报（补充"必须兼容 Python 3.9"） | 指令入消息流；简报新版本生成 | message.created、prompt.updated |
| 3 | 点「继续」 | Run 从 checkpoint 恢复，携带新指令与新 L2 | run.resumed |
| 4 | （可选）用户认为之前 2 个文件也要重做 | 轨迹树上回到分叉点「从此重开」 | 新分支对话（血统记录） |

### 流程 4：审批处理

1. 顶栏铃铛进入审批中心（或 Dashboard「待我处理」）；
2. 逐条或批量处理：PRD 评审（看渲染文档/diff）、计划确认（看板预览 + 增删改）、代码评审（diff + 轨迹摘要）、危险操作（拟执行命令）；
3. 任一审批可「转为对话」：就着审批对象与 Agent 多轮讨论后再决定（评审型对话）；
4. 「修改后恢复」：直接编辑 PRD/WBS → Agent 带修改继续；所有决定写审计事件。

### 流程 5：自然语言操作页面（详见 06 §5）

1. 任意页面按 ⌘K（或点对话气泡图标）呼出命令栏，切到「自然语言」模式；
2. 输入例："把看板切到 v0.2 里程碑，只看 dev-agent 的卡片，然后把 T7 和 T8 都指派给我"；
3. UI-Agent 解析为 3 个界面动作并**逐条预览**（只读动作直接执行，写动作需点确认）；
4. 执行结果以气泡回显，可「撤销」（事件回滚）；整段操作进事件流（actor=ui-agent, on_behalf_of=user）。

### 流程 6：缺陷回流与迭代

1. QA-Agent 测试报告（测试型对话）列出 2 个缺陷 → 自动创建 Bug 工作项挂回原功能，blocked_by 原任务；
2. 用户在功能小图上看到红色依赖边；点 Bug 卡「让 Agent 修」→ 新执行型对话（继承缺陷上下文）；
3. 修复合入后 QA 回归对话自动创建，报告绿了 → Bug 转 done。

### 流程 7：里程碑交付

1. 里程碑页显示 DoD 核对（全部任务 done + 验收审批通过 + 无未决 Bug）；
2. 点「生成交付」→ Release-Agent 对话：产出 release-notes.md（汇总工件与人机轨迹摘要）；
3. 用户审阅发布说明（diff 视图）→ 批准 → 版本 tag + 里程碑关闭事件；
4. 项目活动流与审计页均可回看整个里程碑的人机协作全程。

### 流程 8：审计回溯

1. 审计页过滤：本周 / actor=agent / 结果=auto_granted；
2. 行展开看事件 payload、关联 span、工件 diff；
3. 需要深挖时跳转对应对话的轨迹视图（左树右甘特 + 人机交织时间线，见 05）；
4. 导出 CSV/JSONL（导出本身被审计）。

### 流程 9：资产沉淀与复用（组织记忆闭环，详见 09）

| 步 | 用户操作 | 系统行为 | 落盘 |
| --- | --- | --- | --- |
| 1 | 登录功能验收通过后，在测试报告工件抽屉点「沉淀为资产」 | 弹出表单：目标库=测试库（本体 accepts 过滤）、kind=test-suite、元数据按 schema 校验 | asset.drafted |
| 2 | 补充标题/标签，提交 | 生成入库评审（asset_review Gate），预览资产正文 | asset.in_review、approval.requested |
| 3 | 库评审人批准 | 资产写入资产仓（Git commit），状态 published，来源链记录（项目/工件/commit/对话） | asset.published、asset.linked(provenance) |
| 4 | 数周后新建 B 项目，同类需求 | PM/QA-Agent 起草前调用 `search_assets("登录 回归")` 命中该套件，read + link | asset.consumed、asset.linked(usage) |
| 5 | B 项目改进了套件 → 再次沉淀 | 识别同 kind 近似资产 → 建议建新版本（supersedes 链）而非重复入库 | asset.superseded |

日常入口：左栏 📚 资产库页随时浏览/检索（06 §3.9）；复盘对话（V1.2）由 Agent 产出《沉淀建议清单》批量走步骤 1-3。

## 6. 生命周期六阶段建模（保留自 v0.1，更新挂载关系）

阶段流水线不变，**挂载关系更新为**：Phase 属于项目图（横切所有功能），每阶段的执行落在功能的主对话族里——PM-Agent 的 PRD 对话挂在功能上而非抽象阶段上；Gate 仍是图上的审批节点。各阶段契约：

| 阶段 | 输入 | 执行者 | 产出工件 | Gate |
| --- | --- | --- | --- | --- |
| 1 需求 intake | 一句话/描述/链接 | 人 | requirement.md | 无（提交即入池） |
| 2 需求分析 | requirement.md | PM-Agent（起草对话） | prd.md | ◆ PRD 评审 |
| 3 系统设计 | prd.md | Architect-Agent | design.md | ◆ 设计评审（轻模板可跳过） |
| 4 任务计划 | prd+design | Planner-Agent | wbs.md + 工作项树 | ◆ 计划确认 |
| 5 开发 | Task | Dev-Agent/人（执行对话） | 代码提交+PR 描述 | ◆ 代码评审 + 危险操作即时审批 |
| 6 测试 | 已合代码 | QA-Agent（测试对话） | test-report.md + 缺陷回流 | ◆ 验收（DoD） |
| 7 交付 | 验收通过 | Release-Agent | release-notes.md + tag | ◆ 发布批准（恒审） |

模板两档：**完整**（全七阶段）/ **轻量**（需求→计划→开发→交付，适合个人小项目）；模板由本体（见 08）定义，MVP 内置这两档。工作项模型与状态五桶不变（见 04 数据模型）。

缺陷回流：QA 阶段产生的 Bug 作为新工作项回流开发，图上形成迭代环——"图"优于线性流水线的直接体现。

## 7. 人机分工原则（不变）

人管方向与闸门（提需求、定优先级、阶段门决策、图编排），Agent 管产出与执行（起草、编码、检查、报告）；状态流转双方经同一 API；不确定性高的环节保留人工，重复性高的环节交给 Agent 并通过审批策略逐步放权。
